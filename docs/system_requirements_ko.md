# AI 기반 맞춤형 키오스크 추천 최적화 연구 시스템 구축

## 1. 프로젝트 개요 및 목표

본 프로젝트는 산업공학 학술교류를 위한 AI 기반 키오스크 추천 및 최적화 시스템 연구이다.

연구의 핵심 목적은 고객의 선호도와 매장의 운영 상황을 동시에 고려하여 추천 전략을 최적화하는 것이다.

현재 비교 대상으로 고려하고 있는 모델은 다음 두 가지이다.

1. **고정 가중치 모델(Fixed Weight Model)**: 고객 만족도와 운영 효율성에 관련된 각 요소의 중요도를 일정하게 유지하는 방식
2. **상황별 가중치 모델(Contextual Weight Model)**: 고객 특성과 매장 상황에 따라 각 요소의 중요도를 동적으로 조정하는 방식

두 모델을 동일한 조건에서 학습하고 실험하여, 상황별 가중치 조정이 실제로 더 나은 최적화 결과를 가져오는지 검증하고자 한다.

단, 상황별 가중치 모델의 우수성을 미리 가정하지 말 것. 실험 결과에 따라 고정 가중치 모델이 더 우수하거나 두 모델 사이에 통계적으로 유의미한 차이가 없다는 결론도 도출할 수 있어야 한다.

본 프로젝트는 단순한 추천 프로그램이 아니라, 반복 가능한 실험과 검증을 수행하는 연구 시스템으로 개발한다.

## 2. 개발 환경 및 전체 아키텍처

다음의 네 가지 서비스를 연결하여 개발 환경을 구축한다.

### 2.1. Cloud Codex

역할:
- 소스 코드 작성 및 수정
- 알고리즘 구현과 개선
- 코드 구조 설계
- 테스트 코드 작성
- 버그 수정
- GitHub 저장소 관리
- 실험 결과 분석에 필요한 코드 및 도구 개발

Cloud Codex는 GitHub와 연결된 저장소를 기준으로 작업한다.

### 2.2. GitHub

역할:
- 전체 프로젝트의 중앙 소스 코드 저장소
- Git을 이용한 버전 관리
- 알고리즘별 개발 이력 관리
- 실험 조건과 설정 파일 관리
- 실험별 요약 결과 기록
- 비교 그래프 보관
- 연구 문서 및 실험 기록 관리

가능한 한 GitHub를 중심으로 개발과 실험 과정이 추적되도록 설계한다.

### 2.3. Google Colab

역할:
- 시뮬레이션 실행
- AI 모델 학습
- 대규모 데이터 연산
- 반복 실험
- 실험 결과 분석 및 시각화

실제 연산은 가능한 한 Google Colab의 클라우드 실행 환경에서 수행한다.

사용자의 노트북은 코드 확인, 실험 설정, 실행 명령, 결과 시각화 등의 용도로만 사용하도록 설계한다.

Colab의 CPU, GPU, 메모리와 실행 시간은 가용 자원 및 사용량 제한에 따라 달라질 수 있으므로 환경을 자동으로 확인하여 필요한 자원만 사용한다.

### 2.4. Google Drive

역할:
- 대용량 원시 실험 데이터 저장
- 학습 데이터 저장
- AI 모델의 파라미터 및 가중치 저장
- 시뮬레이션 중간 체크포인트 저장
- 실험 상세 로그 저장
- 데이터 백업

Google Drive에 저장된 각 실험 데이터와 GitHub의 코드 버전 및 실험 기록이 연결되도록 설계한다.

GitHub에는 코드와 소규모 요약 자료를 저장하고, 대용량 데이터는 Google Drive에 저장한다.

## 3. 개발 전 기존 프로젝트 확인

새로운 프로그램을 무조건 처음부터 만들지 말고, 먼저 연결된 GitHub 저장소를 확인한다.

기존 코드나 프로젝트 자료가 존재한다면 다음을 분석한다.

- 기존 추천 알고리즘
- 고정 가중치 모델
- 상황별 가중치 모델
- 고객 만족도 계산 방식
- 재고 및 운영 효율성 계산 방식
- AI 학습 알고리즘
- 시뮬레이션 처리 방식
- 기존 데이터 구조
- 시각화 기능
- 기존에 적용된 연구 가정

기존 연구의 의도와 수학적 모델을 최대한 유지하되, 구조상 문제가 있거나 수정이 필요한 부분은 근거와 함께 정리한다.

기존 코드가 없다면 새 프로젝트를 구성한다.

연구 가정이나 평가 지표가 불명확한 경우 임의로 확정하지 말고, 실행 가능한 기본안을 구현하되 해당 가정을 설정 파일로 분리하고 문서에 명시한다.

기존 파일의 삭제, 대규모 구조 변경, 기존 실험 결과의 덮어쓰기는 피한다.

## 5. 시뮬레이션 환경

### 5.1. 고객 생성

시뮬레이션에서는 가상의 고객이 매장을 방문하는 상황을 생성한다.

사용자가 하루 방문자 수를 직접 설정할 수 있어야 한다.

추후에는 고객 특성, 선호도 분포, 방문 시간대, 매장 상황 등을 조정할 수 있도록 확장 가능한 구조로 구현한다.

고객 데이터 생성 과정에 사용되는 확률분포와 가정은 별도의 설정 파일로 분리한다.

### 5.2. 추천 시스템

두 모델이 동일한 메뉴 후보와 동일한 매장 정보를 기반으로 추천을 수행하도록 한다.

고정 가중치 모델과 상황별 가중치 모델을 구현하되, 두 모델은 가능한 한 공통 인터페이스를 사용하도록 설계한다.

가중치가 사용되는 경우 해당 가중치의 의미와 제약 조건을 명확히 정의한다.

모델이 학습한 결과와 사람이 미리 설정한 규칙을 구분해서 기록한다.

### 5.3. 실제 AI 학습

본 프로젝트에서 중요한 조건은 AI 모델이 단순한 무작위 추천이나 고정 규칙의 반복이 아니라, 데이터를 이용하여 추천 전략을 실제로 개선해야 한다는 점이다.

다음 요소를 명확하게 구분한다.

- 학습 전 초기 모델
- 학습 데이터
- 학습 알고리즘
- 목적함수 또는 보상함수
- 모델 파라미터
- 학습 과정
- 학습 후 성능 평가

고정 가중치 모델은 기본적으로 비교를 위한 기준 모델로 사용하되, 기존 연구 설계에서 고정 가중치 자체를 학습하도록 정의했다면 이를 반영한다.

상황별 가중치 모델은 고객 및 매장 상태를 입력받아 상황에 따라 가중치를 조정하도록 한다.

학습 알고리즘은 기존 코드와 연구 목표를 검토한 뒤 적합한 방식을 선택한다.

초기 구현에서는 과도하게 복잡한 딥러닝 모델보다, 계산 효율적이면서 학습 효과를 검증하기 쉬운 알고리즘을 우선 고려한다.

모델별 학습 시간과 연산 비용도 기록할 수 있도록 한다.

## 6. 두 모델의 공정한 비교

실험의 핵심은 두 모델 사이의 객관적인 성능 비교이다.

비교를 위해 다음 조건을 준수한다.

1. 동일한 고객 생성 조건
2. 동일한 초기 재고와 매장 환경
3. 동일한 메뉴 및 제품 정보
4. 동일한 평가 지표
5. 가능한 한 동일한 난수 시드
6. 동일한 학습 및 평가 예산 또는 그 차이의 명시
7. 학습 데이터와 평가 데이터의 분리

특히 학습 이후 최종 비교는 학습에 사용하지 않은 평가 데이터에서도 실시한다.

재고 변화처럼 추천 행동 자체가 다음 환경에 영향을 주는 경우, 두 모델이 서로 다른 매장 상태를 형성할 수 있음을 고려한다.

이때 동일한 외생적 고객 조건을 사용하되, 모델별 재고와 내부 상태는 독립적으로 관리한다.

결과 비교에서는 평균 성능뿐 아니라 분산, 신뢰구간과 반복 실험 결과를 분석할 수 있도록 한다.

## 7. 시뮬레이션 실행 방식

### 7.1. 설정 인터페이스

Google Colab에서 노트북을 실행하면 사용자가 실험 조건을 쉽게 설정할 수 있는 인터페이스를 제공한다.

필수 입력 항목은 다음과 같다.

- 하루 방문자 수
- 비교할 모델
- 난수 시드
- 체크포인트 저장 주기
- 그래프 출력 여부

추후 설정 가능한 항목을 확장하기 쉬워야 한다.

가능하다면 ipywidgets 기반의 직관적인 인터페이스를 사용한다.

### 7.2. 실행과 중지

시뮬레이션은 하루를 기본 반복 단위로 사용한다.

사용자가 별도로 종료 일수를 지정하지 않는 경우, 중지 요청을 받거나 Colab 실행 환경이 종료될 때까지 반복하도록 구성한다.

단, Google Colab은 무제한 실행을 보장하지 않으므로 실행 중단 및 재개가 가능한 구조여야 한다.

**중지 명령은 하루 단위 경계에서 처리한다.**

현재 처리 중인 하루가 완료되면 데이터를 저장한 뒤 안전하게 종료한다.

### 7.3. 체크포인트 및 실행 재개

시뮬레이션은 주기적으로 다음 정보를 저장한다.

- 현재까지 경과한 날짜
- 모델별 현재 학습 상태
- 모델별 가중치 및 내부 파라미터
- 모델별 재고 상태
- 누적 성능 지표
- 난수 생성기 상태
- 실험 설정과 코드 버전

Colab 세션이 종료되거나 오류가 발생하면 저장된 체크포인트에서 재개할 수 있도록 한다.

체크포인트는 Google Drive에 저장한다.

저장 시 파일 손상을 최소화할 수 있도록 임시 파일 생성 후 교체하는 등의 안전한 저장 방식을 적용한다.

중복 실행이나 중복 데이터 기록이 발생하지 않도록 실험 ID와 진행 상태를 검증한다.

## 8. 실험 데이터 저장 체계

### 8.1. Google Drive

다음의 폴더 구조를 권장한다.

대용량 데이터를 저장할 때는 CSV만 사용하지 말고 Parquet 등 효율적인 파일 형식도 고려한다.

고객 단위 기록을 무조건 전부 보관할 필요는 없다. 원시 데이터의 저장 수준을 설정할 수 있게 하여 스토리지 사용량을 관리한다.

대량의 작은 파일을 Drive에 직접 반복 기록하기보다는 Colab 실행 환경에서 데이터를 모아서 주기적으로 저장하도록 한다.

### 8.2. GitHub

GitHub에는 다음 자료를 보관한다.

- 실험 ID
- 실험 설정
- 사용한 코드의 Git 커밋 해시
- 실행 환경과 라이브러리 버전
- 주요 성능 지표
- 통계 분석 결과
- 비교 그래프
- Drive 데이터 위치를 나타내는 참조 정보

각 실험은 고유한 ID로 관리하며, Drive 데이터와 GitHub 실험 기록이 서로 연결되어야 한다.

대용량 원시 데이터는 일반 Git 저장소에 업로드하지 않는다.

실험 결과를 GitHub에 기록하는 자동화 기능을 구현할 경우, 기존 기록을 덮어쓰지 않고 새 실험 결과를 추가하는 방식으로 구성한다.

## 9. 시각화 및 결과 분석

시뮬레이션이 중지되거나 지정된 평가 시점에 도달하면 실험 결과를 그래프로 보여준다.

최소한 다음 시각화 기능을 구현한다.

1. 날짜별 고객 만족도 변화
2. 모델별 평균 만족도 비교
3. 상황별 가중치 변화
4. 모델별 목적함수 또는 보상값 변화
5. 학습 진행에 따른 성능 변화
6. 재고 및 운영 효율성 변화
7. 모델 간 성능 차이의 변화
8. 반복 실험 결과의 분포 및 신뢰구간

단, 실제로 정의되지 않았거나 측정할 수 없는 지표를 임의로 생성하지 않는다.

그래프는 Colab에서 직접 확인할 수 있어야 하며, 주요 그래프는 이미지 파일로 저장하도록 한다.

분석 결과에는 가능한 한 실험 조건과 사용한 코드 버전을 함께 표시한다.

## 10. 실험 자동화 및 재현성

연구의 신뢰성을 위해 같은 조건에서 실험을 다시 수행할 수 있어야 한다.

이를 위해 다음 기능을 구현한다.

- 실험별 고유 ID 생성
- 난수 시드 관리
- 설정 파일 저장
- 코드 버전 기록
- 실험 환경 기록
- 모델 파라미터 저장
- 학습 및 평가 결과 분리
- 반복 실험 자동화
- 기존 결과와 새로운 결과 비교

또한 GitHub Actions를 이용해 소규모 단위 테스트와 코드 품질 검사를 자동 실행할 수 있도록 구성한다.

다만 GitHub Actions를 Colab의 지속적인 실행을 보장하는 도구로 취급하지 않는다.

## 11. 보안 및 인증

Google Drive와 GitHub 연동을 위한 인증 정보를 소스 코드에 직접 삽입하지 않는다.

Colab의 Secrets 기능이나 적절한 인증 방법을 사용한다.

GitHub 토큰, 개인 인증키, Google 인증 파일은 Git 저장소에 업로드하지 않는다.

가능하면 최소 권한 원칙을 적용한다.

GitHub에 자동 업로드할 경우 실험 기록용 브랜치를 이용하거나 Pull Request를 생성하는 방식도 고려한다.
